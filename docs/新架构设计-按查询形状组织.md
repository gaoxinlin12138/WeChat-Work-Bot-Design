# 新架构设计：按「查询形状」组织的管道

> 当前状态（2026-10-10）：产品查询 V2 已切为唯一运行链路；legacy、shadow、off
> 兼容分支已删除。本文保留查询形状、校验边界和后续拆分方向，代码落点以
> `app/business/tools/product.py`、`app/business/product_query.py` 和 `app/ontology/` 为准。

> 出发点：现有系统**不是白写的** —— 清单、明细、统计、翻页、脱敏、媒体、制度检索、话术
> 这些能力都已经能跑，问题在于它们**摆放的位置**是一条"守卫链"，
> 于是"改一点冒一点、永远改不完"。
>
> 这次设计的目标是**重新摆放**，不是重写。

---

## 0. 要解决的三件事

| 现象 | 根因 |
|---|---|
| 一问就出错 | 方向瞄准了"意图识别"，而错误都在意图**之后**（值→字段、校验、算子、上下文、渲染） |
| 改一点冒一点 | 守卫散布在整条链上（依据→权限→字段→上下文→算子→渲染），加一个特例就碰坏另一个 |
| 永远改不完 | 没有验收标准，"改好了"没有定义 |

---

## 1. 顶层结构

```
                        员工消息（企微）
                              │
                    ┌─────────▼─────────┐
                    │   ① 域路由         │  只判断：制度 / 话术 / 产品 / 闲聊通用
                    └─────────┬─────────┘
             ┌────────────────┼────────────────┐
             ▼                ▼                ▼
        【制度域】        【话术域】        【产品域】
        向量检索+重排      场景匹配      ★ 形状管道（本设计的核心）
             │                │                │
             └────────────────┼────────────────┘
                              ▼
                    ┌───────────────────┐
                    │  统一回答契约      │  content / sources / outcome / 降级说明
                    └─────────┬─────────┘
                              ▼
                    ┌───────────────────┐
                    │  交付层            │  排版 / 分页 / 脱敏 / 发送 / 去重
                    └───────────────────┘
```

**为什么域要分开**：三类内容形态不同，检索方式必须不同。

| 域 | 形态 | 引擎 | 现状 |
|---|---|---|---|
| 制度 | 非结构化长文本 | 向量检索 + 重排 | ✅ 已有（66 chunks） |
| 话术 | 半结构化（场景→话术） | 场景匹配 | ✅ 已有（44 条） |
| 产品 | **结构化表格** | **V2 参数化精确查询（不走向量检索）** | ✅ 唯一运行链路 |

## 2. 形状契约（本设计的核心）

**每一种问题都必须先归到一个"形状"上。形状是有限可枚举的** —— 这是整个设计的地基。

| 形状 | 员工会怎么说 | 执行 | 呈现 |
|---|---|---|---|
| `detail` | "LY0653GDT 的材质" | 按型号取一款，投影指定字段 | 字段：值 |
| `detail_full` | "LY0653GDT 的全部参数" | 同上，投影=全字段 | 完整资料（含配件明细） |
| `listing` | "灰玻璃·枪灰的产品有哪些" | 条件查询 + 分页 | **每款一行** + 下一页 |
| `rank` | "最贵的/前三名/第二贵" | 排序 + limit | 排序清单 |
| `aggregate` | "一共有多少种颜色"/"平均价"/"共几款" | 去重计数 / 最值 / 平均 / 求和 / 计数 | 数字 + 分布 + 分页 |
| `compare` | "0653 和 0669 哪个贵" | 取多款 + 逐字段对比 | 横向对比 |
| `media` | "发我 0653 的视频" | 媒体表 | 发送附件 |
| `policy` | "报销标准是多少" | 向量检索 | 引用段落 |
| `script` | "客户嫌贵怎么回" | 场景匹配 | 话术 |
| `chitchat` | "你好" | 直接答 | 引导 |
| `out_of_scope` | 与库无关的通用问题 | 模型自由答 | 明确标注"非公司资料" |

**`out_of_scope` 是新增的一等形状** —— 这就是"豆包式的部分"：不碰你的数据，
可以让模型自由回答；碰数据的形状一律走库，**查不到就说查不到**。

### QueryIntent（形状契约的数据结构）

```python
@dataclass(frozen=True)
class QueryIntent:
    shape: Shape                      # 上表之一（必填，唯一入口）
    subject: Subject                  # 查询对象：全部产品 / 某型号 / 某条件集
    projection: tuple[str, ...]       # 要显示的字段
    filters: tuple[Filter, ...]       # 条件（已通过取值目录归一）
    aggregate: Aggregate | None       # 统计描述
    order: Order | None               # 排序（字段 + 方向 + 取前 N）
    page: int
    # 追踪用：哪个环节产出的、依据是什么
    provenance: Provenance
```

**关键约束**：`shape` 缺省即失败 —— 不允许"没有形状"的执行。

## 3. 五个环节（守卫只在一处）

```
员工问句
  │
  ├─① 形状解析 ShapeParser ──────── 模型 + 规则：模糊 → 确定（唯一允许"猜"的地方）
  │
  ├─② 形状校验 ShapeValidator ───── ★ 唯一的守卫处
  │      · 值 → 字段（查取值目录）
  │      · 写法归一（"灰玻璃枪灰" → "灰玻璃·枪灰"）
  │      · 权限（成本价 / 采购价）
  │      · 依据（是否在原话里）
  │      · 不可判定 → 产出 clarification（**不是 refusal**）
  │      · 缺字段 → 按形状补默认投影（不再"无法可靠确认"）
  │
  ├─③ 执行器 Executors ──────────── 一个形状一个执行器，互不干扰
  │      detail / listing / rank / aggregate / compare / media
  │
  ├─④ 呈现器 Renderers ──────────── 一个形状一个渲染器
  │
  └─⑤ 兜底层 Fallback ──────────── ★ 永不冷场
         查不到 → "最接近能答的" + "怎么问才能答"
         例：300块以内 没这个概念 →
             "产品库里没有'300块以内'这种说法。按价格筛可以这样问：
              '300元以内的套装'（现有 12 款）"
```

### ①②③④⑤ 的边界规则

- **① 可以猜**（模型输出模糊的东西）
- **② 不许猜**：只做"能不能确定"的判定，要么通过、要么降级为澄清
- **③④ 不许拒答**：形状已定，执行和渲染是确定的
- **⑤ 不许装懂**：查不到就说查不到，并给出路

**这一条是"改一点冒一点"的解药**：加一个新形状 = 加一个执行器 + 一个渲染器，
**碰不到任何已有形状**；所有守卫收敛在②，不会再有"改 A 处坏 B 处"。

## 4. 取值目录（准确性的基础设施）

产品域的每个可筛字段都登记它的取值：

```
color     → 灰玻璃·枪灰 / 奶白玻璃·奶白 / 镜面玻璃·镜面 / …（12 种）
material  → 全铜 / ABS外壳铜水路 / 304钢壳铜水路 / …（10 种）
档位       → 2 / 3 / 4
备注       → 10只装 / 5只装 / …
```

三个用途（本次已验证有效）：

1. **值 → 字段**：员工说"镜面玻璃·镜面"，系统知道它是颜色而不是系列（此前模型猜错 → 0 款）
2. **写法归一**：`灰玻璃枪灰` → `灰玻璃·枪灰`（员工漏打间隔号）
3. **喂给模型**：低基数字段（颜色/材质/档位）的取值可以放进提示词，从源头减少乱猜

**字段与取值的区分**是这个系统的准确性命门：
模型知道字段**名**，但没有字段**取值**的概念 —— 这是之前一半错误的来源。

## 5. 上下文层（焦点机制）

现在上下文散落在七八处（pending 槽位、catalog context、selected ids、state…），
规则不统一 → "那三款多少钱"、"第二个多少钱"接不上。

新设计：**只维护一个"当前焦点"**。

```python
@dataclass(frozen=True)
class Focus:
    intent: QueryIntent          # 上次的完整意图
    result_ids: tuple[str, ...]  # 上次的结果（用于"第二个"、"那三款"）
    shown_values: tuple[str, ...] # 上次展示的取值（用于"哪三款"）
    turn: int
```

追问处理流程（**统一在①之前**）：

```
问句 → 判断是否为追问（省略/指代/序数/翻页）
       ├ 是 → 用 Focus 把问句**补全成完整问题** → 走形状管道
       └ 否 → 清空 Focus → 走形状管道
```

明确规则（现在是隐含的、散落的）：

| 情况 | 行为 |
|---|---|
| 明确型号 / 新条件 | 独立，清焦点 |
| "它/这个/第二个/那三款" | 继承 subject，保留其他 |
| "下一页 / 第N页" | 继承 intent，只改 page |
| 承接统计结果追问 | 继承 filters，改 shape |

## 6. 验收体系（定义"完成"）

**这是当前最缺的一块，也是"永远改不完"的解药。**

```
evals/
  shapes.jsonl       每个形状 5~10 条真实问法 + 期望答案（可机器判定）
  followups.jsonl    追问 20 条（多轮）
  out_of_scope.jsonl 应走通用回答或应明确拒答的
  policy.jsonl       制度 23 条（已有）
```

`scripts/evaluate_shapes.py` 输出四个**分开**的指标：

| 指标 | 含义 | 容忍度 |
|---|---|---|
| **形状解析准确率** | 问句归到对的形状了吗 | 目标 ≥ 95% |
| **执行准确率** | 形状对了，结果对吗 | 目标 ≥ 98% |
| **答错率** | 给了**错误**答案 | **零容忍**（报错价有商业后果） |
| **拒答率** | 没能回答（澄清/查不到） | 尽量低，但**不作为硬指标** |

**拒答与答错必须分开统计** —— 现在混着看，所以显得"到处都是问题"。
两者性质完全不同：拒答是体验问题，答错是事故。

## 8. 迁移路径（4 步，每步都能独立上线）

| 阶段 | 做什么 | 风险 | 产出 |
|---|---|---|---|
| **0** | 建 `shapes.jsonl` + 评测脚本，量出**当前**的形状解析/执行/答错/拒答 | 不动生产代码 | 一张基线表 |
| **1** | 产品域执行器按形状归位（清单/明细/统计/翻页/媒体基本可直接搬） | 中（重构） | "改一点冒一点"开始消失 |
| **2** | 守卫收敛到 `validator.py` 一处 | 中 | 拒答可控、可统计 |
| **3** | 补缺失形状：`rank`、`compare` 增强、追问统一 | 低（新增） | 探针剩余 3 类清零 |
| **4** | 兜底层（不冷场）+ `out_of_scope`（通用问答） | 低 | 员工体感明显变化 |

**建议顺序：0 → 4 → 3 → 1 → 2。**
先做 0（有基线才好判断）、4（体感提升最快、风险最低）、3（补齐缺的形状），
最后做 1、2（结构性搬迁，风险最高但收益最持久）。

## 9. 三个痛点的对应解

| 你的痛点 | 新架构怎么解 |
|---|---|
| **"一问就出错"** | 问句先归形状 → 形状有限（11 种）→ 每类只有一条执行路径 → 出错必能定位到"哪个形状的哪一环" |
| **"改一点冒一点"** | 守卫集中在一处；加形状不碰别的形状；执行器与呈现器一一对应 |
| **"永远改不完"** | 形状可枚举 + 每类有期望答案 → 通过率有分母；拒答与答错分开 → 知道该优化哪个 |

---

## 10. 不做什么（边界）

- **产品价格/参数不由模型生成** —— 一律走库。这是唯一不让步的地方。
- **不做"什么都能答"的通用助手** —— 碰数据的问题查不到就说查不到；
  不碰数据的（`out_of_scope`）才交给模型自由答。
- **不追求"零拒答"** —— 追求"零答错"；拒答要少，但不能用准确性换。
