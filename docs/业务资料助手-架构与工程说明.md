# 业务资料助手：架构与工程说明

更新时间：2026-10-12

本文是当前代码的架构事实说明。若本文与旧的设计草稿冲突，以生产代码、测试和本文件为准。

## 1. 当前结论

- 线上只有一条 LangGraph 生产主链：主链 → 领域工具 → 各领域执行器 → 统一回答；其中产品/媒体领域使用既有 V2 结构化执行器。
- 统一 `QueryPlan` 已接入产品/媒体任务的生产计划阶段，负责标准化、字段与证据校验、权限审查和确定性纠偏。
- `ProductQuery` 是产品查询契约，`product.py` + `product_store.py` 是产品结构化查询的唯一生产执行路径；QueryPlan 不直接执行 SQL，也不产生第二份答案。
- QueryPlan 校验失败时，生产计划安全回退到原 V2 计划；可通过 `UNIFIED_QUERY_PLAN_ENABLED=false` 临时关闭接入。
- 制度、通用资料和话术仍走各自领域执行器，不会被产品 QueryPlan 强行转换。

## 2. 生产回答链路

```text
企业微信员工
    │
    ▼
app/wecom/long_connection.py
    │  接收、去重、身份与会话上下文
    ▼
app/business/graph/builder.py
    │  normalize_input → create_plan → execute_task
    │                  → verify_results → finalize_reply
    │
    ├─ 制度/通用资料 → tools/knowledge.py → RAG 检索与回答
    ├─ 产品/产品媒体 ─┬→ QueryPlan 校验/审查/桥接
    │                 └→ tools/product.py / tools/media.py
    │                    → product.py → product_store.py → PostgreSQL
    ├─ 客户话术 → graph/reply_script.py → tools/reply_script.py
    └─ 闲聊 → 确定性欢迎/引导
    │
    ▼
统一 RoutedReply（产品 V2 额外生成 ResponseEnvelope 做结果治理）
    │  来源、权限、输出预算、审计追踪
    ▼
企业微信回复或管理台测试结果
```

### QueryPlan 在生产中的位置

```text
模型提出 ProductQuery（模型不可用或失败时规则兜底）
        ↓
query_plan_from_product_query()
        ↓
review_query_plan()
        ├─ 通过：product_query_from_plan() → 既有 V2 执行器
        └─ 异常：保留原 V2 计划，走安全回退
```

这是一条链路中的“计划契约层”，不是新的回答链路。`builder.py` 收尾时还会把统一计划和审查结果写入 execution trace，方便审计和回放。

## 3. 领域边界

| 领域 | 生产入口 | 事实来源/执行器 | QueryPlan 状态 |
|---|---|---|---|
| 产品资料 | `app/business/tools/product.py` | `product_query.py` + `product_store.py` + PostgreSQL | 已接入生产计划阶段 |
| 产品图片/视频 | `app/business/tools/media.py` | 产品媒体表、本地媒体文件、企业微信发送 | 通过媒体形状校验后执行 |
| 制度资料 | `app/business/tools/knowledge.py` | `app/knowledge/`、关键词/向量检索 | QueryPlan 协议已预留，尚未接入生产审查 |
| 通用资料 | `app/business/tools/knowledge.py` | RAG/资料检索 | 保持原领域路径 |
| 客户话术 | `app/business/tools/reply_script.py`、`graph/reply_script.py` | 已发布话术和会话字段 | QueryPlan 协议已预留，尚未接入生产审查 |
| 闲聊 | `builder.py` | 确定性回复 | 不进入业务资料执行器 |

## 5. 启动和验证

```powershell
# 推荐：启动 API、管理台、Redis（按配置）和企业微信长连接
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start_all.ps1

# 管理台
http://127.0.0.1:8000/admin

# 存活与就绪检查
Invoke-RestMethod http://127.0.0.1:8000/health
Invoke-RestMethod http://127.0.0.1:8000/health/ready

# 代码更新后重启，确保进程加载最新代码
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\stop_all.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start_all.ps1
```

`/health=ok` 只表示 Web 进程存活；`/health/ready=200` 表示当前部署要求的数据库、模型和向量检查通过，Redis 与企业微信可为 `ok` 或按部署选择保持 `not_configured`。开发环境可能因未配置 embedding 或通讯录而返回 `503 degraded`，不等于产品 V2 查询代码失效。

## 6. 配置开关

| 环境变量 | 默认值 | 作用 |
|---|---:|---|
| `TASK_PLANNER_ENABLED` | `true` | 是否允许模型参与任务规划；关闭后走规则计划 |
| `UNIFIED_QUERY_PLAN_ENABLED` | `true` | 是否在产品/媒体生产计划阶段启用 QueryPlan 审查与桥接 |
| `LANGGRAPH_CHECKPOINT_ENABLED` | `false` | 是否启用 PostgreSQL checkpoint；开启前需做隔离库恢复验证 |
| `REDIS_URL` | 空 | 跨进程会话与缓存；生产环境必须配置 |
| `EMBEDDING_*` | 空 | 制度/通用资料向量检索；产品结构化查询不依赖向量 |

## 7. 当前已知边界

- 仍是单机文件存储，尚无对象存储、独立解析 Worker 或正式版本化数据库迁移。
- 图片型或文本层不足的制度 PDF 当前只标记 `needs_ocr`，项目没有内置云端视觉 OCR 服务，需要人工或外部 OCR 处理。
- QueryPlan 已接入产品/媒体生产规划，但制度和话术仍使用各自稳定执行器。
- 真实产品质量评测依赖当前发布目录；历史型号不存在时，评测中的 no-result 是资料覆盖问题，不是计划错误。
- 全量测试中的 PDF 资产用例需要工作区提供 3 个原始 PDF；缺失资产时这两个用例会失败，其他代码回归不受影响。
- 生产环境仍应定期检查 `/health/ready`、长连接认证日志、数据库备份和磁盘空间。

## 8. LangGraph 主链、会话与 checkpoint

当前图主链固定为：

```text
normalize_input → create_plan → execute_task → verify_results → finalize_reply
```

- 简单问题是单任务计划，复合问题最多拆成四个只读任务；执行节点循环调用已有领域工具。
- 图状态只保存可序列化数据；Agent、流式回调和权限上下文通过 Runtime Context 传入。
- `BusinessAgent.answer()` 对外契约保持不变。企业微信 `msgid` 先去重，再以哈希形式进入图状态和审计。
- Redis 优先保存跨消息业务会话；未配置或暂时不可用时会退回进程内内存，因此只能保证单进程临时可用，不能保证跨进程或重启后恢复。PostgreSQL checkpoint 由 `LANGGRAPH_CHECKPOINT_ENABLED` 控制，默认关闭，启用前要在隔离库验证旧数据兼容、保留期和清理方案。
- 客户话术是 `load_session → collect_fields → generate_reply` 子图；缺字段时暂停并等待下一轮消息。

## 9. QueryPlan 与 V2 的生产契约

产品和媒体请求的执行契约是：

```text
模型提出 ProductQuery（模型不可用或失败时由规则计划兜底）
    → query_plan_from_product_query()
    → review_query_plan()
    → product_query_from_plan()
    → product.py / product_store.py / PostgreSQL
    → 统一回答
```

QueryPlan 负责标准化形状、字段、筛选、排序、聚合、分页、证据和权限边界；它不执行 SQL、不调用任意工具、不写库，也不生成产品事实。桥接失败或审查异常时，`builder.py` 保留原 V2 计划安全回退；`UNIFIED_QUERY_PLAN_ENABLED=false` 可临时关闭这层接入。

因此，生产环境仍然只有一条回答链路：LangGraph 主图 → 领域工具 → 各领域执行器 → 统一回答。QueryPlan 是产品/媒体路径内的计划契约和审查层，不是第二条回答链路。制度、通用资料和话术继续由各自稳定执行器处理。

## 10. 查询形状与意图路由

查询形状是有限、可审计的执行契约。当前真正接入生产 QueryPlan 的是产品和媒体形状；制度、话术、闲聊和 `out_of_scope` 目前只是协议注册表中的预留形状，不代表已经接入生产执行链路。

| 形状 | 典型问题 | 执行边界 | 当前状态 |
|---|---|---|---|
| `detail` | 某型号的材质/颜色 | 指定型号 + 指定字段 | 产品 QueryPlan + V2 |
| `detail_full` | 某型号全部参数 | 指定型号 + 全字段投影 | 产品 QueryPlan + V2 |
| `listing` | 符合条件的产品有哪些 | 条件查询 + 分页 | 产品 QueryPlan + V2 |
| `count` / `aggregate` | 有多少款、多少种颜色、平均价 | 受注册表约束的计数、去重、最值、平均等 | 产品 QueryPlan + V2 |
| `rank` | 最贵、最便宜、前三名 | 排序 + limit | 产品 QueryPlan + V2 |
| `compare` | 两款哪个贵/参数差异 | 多对象取数 + 字段对比 | 产品 QueryPlan + V2 |
| `media` | 发某型号图片/视频 | 媒体表与发送权限 | 媒体 QueryPlan + 媒体执行器 |
| `policy` | 报销标准 | 制度检索与引用 | 协议预留，生产未接入 |
| `script` | 客户嫌贵怎么回 | 已发布话术匹配 | 协议预留，生产未接入 |
| `chitchat` / `out_of_scope` | 你好、与公司资料无关的问题 | 确定性引导或普通资料路径 | 协议预留/由现有 Intent 处理 |

意图与任务规划采用“确定性状态接回 → 模型优先 → 规则兜底”的顺序，但不是所有请求都必须调用模型：明确问候、资料候选编号、已确认的翻页或续问等确定性状态可以直接处理。其余请求在模型可用时先调用结构化意图模型；产品/媒体任务随后再调用结构化任务规划模型。模型不可用、调用失败或 JSON/枚举校验失败时，才退回高精度规则和普通规则计划。服务端随后执行字段、证据、权限和上下文校验，再进入 QueryPlan 审查。模型置信度是自报值，不等于校准后的正确概率；低置信度或对象不明时应澄清，不凭空补造事实。

上下文由产品焦点、待补字段、已选候选、上一轮媒体列表等状态共同恢复。明确新型号或新条件会清理旧焦点；“它/第二个/下一页/那三款”等追问继承上一轮可验证的结果。

## 11. 本体、取值目录与治理边界

本体的实际落地点是 `app/ontology/schema.py`、`app/ontology/values.py` 以及产品查询和治理注册表。它们用于区分分类维度与标识字段、归一化字段取值、限制可聚合字段、校验权限和输出预算。例如型号/系列是标识符，不应被当作“分类种类”直接统计；颜色、材质等取值要先做“值 → 字段”归一。

目前已经落地：

- 固定列映射和参数化 SQL，模型不能生成 SQL 或任意函数名。
- 产品/媒体 QueryPlan 的字段、操作符、型号依据、敏感字段和交付方式由服务端校验。
- 结果总数、列表、页码、游标、截断原因和来源摘要等结构化输出。
- 统一 execution trace，记录计划、审查、结果摘要和降级原因。

仍属于后续规划：正式的派生维度/关系目录、自动生成的完整本体提示、跨产品关系查询和正式数据库迁移。实现这些内容前，应先补能力注册表、执行器和评测样本，不能只修改提示词。

## 12. 评测、回放与验收口径

- 固定影子语料：`scripts/evaluate_query_shadow.py` + `evals/shadow_query_cases.jsonl`。
- 真实审计原始回放：`scripts/export_audit_queries.py` + `scripts/evaluate_replay.py`；原始问句保留在 `tmp/audit-export/queries.jsonl`。
- 真实业务库只读 QueryPlan 对比：`scripts/evaluate_query_plan_readonly.py`。
- 字段、权限和多轮上下文评测：`scripts/evaluate_product_fields.py`、`scripts/evaluate_context_inheritance.py`。

2026-10-12 的真实只读回放包含 19 条去重后的真实审计问题，均完成新侧只读执行；计划校验失败 0 条、形状差异 0 条、预期纠偏 1 条。其中 1 条因旧侧没有可比较的产品计划，未完成新旧计划对比。该回放使用规则路径，不代表线上 `planner_model` 路径。“最便宜的产品多少钱”改为直接回答最低已登记套装价，属于正确改进。线上冒烟已验证最低价、完整详情和产品列表。

验收时要把“答错”和“澄清/查不到”分开统计；固定评测集全通过不能等同于线上 100% 准确。当前全量 pytest 的两个失败来自工作区缺少三个既有 PDF 测试资产，不是 QueryPlan 接入造成的代码回归。

## 13. 当前边界与后续路线

1. 继续保持产品结构化查询的零自由生成边界；所有产品事实必须来自数据库结果。
2. QueryPlan 协议已支持制度和话术的离线校验，但尚未接入生产审查；如后续接入，先补领域证据、发布状态和执行器验收，再替换各自稳定执行器。
3. 生产部署前验证 checkpoint 旧数据、备份恢复、多 worker 和长连接重启；部署后观测延迟、审查失败率和 checkpoint 表增长。
4. 业务库扩充后重新运行真实只读评测；历史型号不存在时的 no-result 应归为资料覆盖问题，不能直接算理解失败。
5. 若新增跨域查询、供应商聚合或发送动作，先扩展形状契约、权限和评测，再开放生产执行。
