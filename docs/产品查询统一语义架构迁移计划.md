# 产品查询统一语义架构迁移计划

更新时间：2026-10-13

## 一、改造目标

把当前“意图识别、任务规划、产品前置解析、上下文恢复、QueryPlan、V2 兼容”多处共同解释自然语言的链路，收敛为一条统一的语义入口：

```text
企业微信原话 + 身份 + 会话快照
        ↓
统一语义解析器
        ↓
CanonicalRequest JSON
        ↓
服务端指代解析、字段/取值/权限校验
        ↓
固定 QueryPlan
        ↓
参数化查询或媒体执行器
        ↓
基于真实结果的回答
        ↓
审计、会话快照和评测记录
```

核心边界保持为：

- 大模型负责理解自然语言、抽取意图、对象、字段和约束；
- 服务端负责指代确认、字段白名单、取值标准化、权限、分页、排序和风险校验；
- 数据库和已发布产品目录负责事实；
- 执行器只接受经过校验的结构化计划；
- 回答只能引用真实结果，不允许模型补造产品事实。

## 二、当前基线

当前代码已经具备相当一部分目标能力：

- `app/business/graph/builder.py` 已有 LangGraph 主链；
- `app/business/query_plan.py` 已有统一计划契约、字段校验、证据校验、分页和权限审查；
- `app/business/canonical.py` 已有 `CanonicalRequest`，但目前主要位于规划链路末端；
- `app/business/product_focus.py` 已保存结果 ID、型号、可信 ID、页码、查询指纹和过期时间；
- `app/business/product_store.py` 使用固定列映射和参数化 SQL；
- `app/business/query_governance.py` 已有能力注册表、输出预算和敏感字段保护；
- 产品资料已有草稿、发布快照、媒体关联和审计轨迹；
- `tests/`、`evals/` 和 `docs/全场景测试方案.md` 已提供回归和影子评测入口。

当前主要问题不是缺少单个功能，而是同一条自然语言仍可能被多个层次分别解释。`TaskPlan`、`ProductQuery`、规则前置解析器和旧 V2 兼容路径同时存在，导致一个层次得到的结论可能被另一个层次改写。此前“他的材质是什么”被解析成 `material contains 他`，就是这种结构性风险的具体表现。

## 三、目标架构

### 3.1 统一入口

所有进入产品域的消息都必须经过同一个语义入口，并产生同一种结构化结果：

```text
parse_semantic_request(raw_message, identity, session_snapshot)
    → CanonicalRequest
```

确定性快捷路径可以继续保留，但只能作为性能优化。即使跳过模型，也必须直接生成完全相同的 `CanonicalRequest`，不能生成另一套私有语义对象。

### 3.2 规范 JSON

建议把当前 `CanonicalRequest` 和 `QueryPlan` 合并成一个版本化的边界协议，初版至少包含：

```json
{
  "version": 2,
  "request_id": "req-...",
  "raw_query": "他的材质是什么",
  "domain": "product",
  "shape": "detail",
  "target": {
    "kind": "context",
    "value": "LY0601GT-Cu",
    "resolved_id": "product-uuid",
    "source": "trusted_focus",
    "evidence": "他"
  },
  "fields": [
    {
      "name": "material",
      "evidence": "材质",
      "source": "current"
    }
  ],
  "filters": [],
  "sort": [],
  "page": 1,
  "page_size": 1,
  "context_mode": "continuation",
  "confidence": 0.96,
  "ambiguities": [],
  "needs_clarification": false,
  "clarification_question": "",
  "parser_version": "semantic-v1",
  "model_metadata": {
    "provider": "...",
    "model": "...",
    "prompt_version": "..."
  }
}
```

这里必须同时保存 `raw_query` 和结构化结果。不能只把原话裁剪成“主干”，因为否定词、范围、数量、顺序和例外条件都可能改变查询结果。

### 3.3 执行边界

语义解析器不能输出 SQL、表名、列名拼接片段、任意工具名或函数名。后端根据 `domain、shape、fields、filters、sort` 选择固定执行器，再由执行器生成参数化查询。

模型可以提出“上一轮那个产品”，但最终的 `resolved_id` 必须来自服务器保存的 `ProductFocus`、已返回结果或数据库精确匹配。无法确认时必须澄清，不得把模型猜测直接当成产品 ID。

## 四、分阶段实施计划

### 阶段 0：建立基线和冻结行为（P0，1～2 天）

目标是先知道改造前的真实质量，避免重构后只凭感觉判断好坏。

任务：

1. 从现有审计日志和人工记录整理至少 200 条真实产品问句；
2. 按独立查询、详情、筛选、价格、库存、媒体、多轮指代、序号、分页、比较、推荐、权限、空结果和歧义分类；
3. 每条记录标注期望的 `domain、shape、target、fields、filters、needs_clarification`；
4. 记录当前链路的回答、耗时、回退次数、澄清率和错误类型；
5. 把“他的材质是什么”“它的图片”“第二个的价格”“不要成本价”等历史问题加入固定回归集；
6. 统一定义“答错、澄清、查不到、权限拒绝、系统失败”五种结果，不再把它们混成一个失败率。

交付物：

- `evals/product_semantic_golden.jsonl`；
- 基线评测报告；
- 现有字段、操作和权限清单；
- 兼容行为清单。

通过标准：固定语料能够重复运行，并能分别统计解析错误和数据无结果。

### 阶段 1：冻结统一协议（P0，2～3 天）

任务：

1. 决定 `CanonicalRequest v2` 的字段、枚举和版本策略；
2. 使用 Pydantic 或等价的严格 schema 描述协议；
3. 固定 `domain、shape、target、fields、filters、sort、aggregate、delivery、context_mode、clarification` 的允许值；
4. 为每个字段规定 `evidence、source、required_permission、value_type`；
5. 明确未知字段、缺失主体、非法操作、低置信度和歧义的错误码；
6. 编写模型 JSON Schema 和人工可读协议文档；
7. 规定解析器版本、Prompt 版本和模型版本如何写入审计。

建议的产品查询形状：

- `detail`：指定产品的指定字段；
- `detail_full`：指定产品的完整已发布资料；
- `listing`：条件筛选并分页；
- `count`：产品实体数量；
- `aggregate`：颜色、材质等去重统计，或价格/件数聚合；
- `rank`：固定排序后的前几项；
- `compare`：最多三款产品比较；
- `media`：查询或发送已发布图片、视频。

通过标准：同一个 JSON 在本地解析、审查、回放和生产执行中含义一致；未知字段不能静默放行。

### 阶段 2：实现统一语义解析器（P0，3～5 天）

新增一个独立模块，例如 `app/business/semantic_parser.py`，负责：

1. 接收原话、身份摘要和经过脱敏的会话快照；
2. 调用统一的 `LLMAdapter.parse_request()`；
3. 解析严格 JSON，并拒绝未知键、非法枚举和危险内容；
4. 保留原话证据，不允许模型把证据改写成不存在的表达；
5. 对明确问候、已确认翻页、媒体待补型号等场景，可以使用确定性快捷路径；
6. 快捷路径必须生成同样的 `CanonicalRequest`；
7. 失败时进入规则兜底或澄清，不直接进入产品执行器。

需要逐步停止以下模块对自然语言做独立最终判断：

- `intent.py` 中只负责意图的旧输出；
- `planner.py` 中自行拼装的旧 `TaskPlan`；
- `product_query.py` 中把自然语言直接解释成业务条件的前置逻辑；
- 产品工具中再次根据原话猜字段或价格范围的分支。

这些模块可以暂时保留为适配器或校验器，但不能再产生与统一协议竞争的第二个最终结论。

通过标准：同一个输入只产生一个可追踪的语义计划；“他的材质是什么”不会产生 `material=他`；大模型不可用时仍能安全澄清或走有限的规则兜底。

### 阶段 3：统一指代和会话解析（P0，3～5 天）

任务：

1. 把 `ProductFocus` 作为产品域唯一可信上下文；
2. 统一保存上轮查询计划、结果 ID、结果型号、可信 ID、页码、总数、查询指纹、过期时间和待补动作；
3. 将“它、他、这个、那个、第二个、后一页、那几个”等表达解析成 `target.kind=context` 或分页动作；
4. 明确单候选、多候选、无候选和过期候选的行为；
5. 明确新型号、新筛选条件和跨域问题何时清理旧焦点；
6. 任何无法唯一确认的对象都输出澄清，不将模型猜测写入可信 ID；
7. 为同一用户的并发消息增加版本或请求序号，防止旧响应覆盖新焦点。

重点回归场景：

- “LY0601GT-Cu详细信息” → 详情；
- “他的材质是什么” → 同一产品的材质；
- “把它的图片和视频都发我” → 两个媒体任务；
- “刚才那几个里第二个的价格” → 当前候选中的第二个；
- 多候选时直接说“它” → 澄清；
- 上下文过期时说“它” → 澄清；
- 新型号出现后不能继承上一轮筛选条件。

通过标准：指代解析只使用可信会话状态，不把模型生成的任意型号当成事实。

### 阶段 4：把校验和执行收敛成一条链（P0，4～7 天）

目标是让 `QueryPlan` 变成统一 JSON 的服务端执行计划，同时保留旧 V2 作为短期兼容实现，而不是第二套语义系统。

任务：

1. 增加 `CanonicalRequest → QueryPlan` 的单向转换器；
2. 保留 `ProductQuery` 作为执行器兼容对象，但禁止它重新解释原话；
3. 统一字段白名单、值目录、操作符、聚合能力、分页上限和敏感权限；
4. 对模型明确说出的每个条件做证据覆盖检查；
5. 对否定条件、区间条件、数量条件和排序条件做完整性检查；
6. 所有查询使用固定列映射和参数化 SQL；
7. QueryPlan 审查失败时记录明确错误码，并根据错误类型选择澄清、拒绝或兼容回退；
8. 回退必须写入 execution trace，不能静默发生；
9. 回答前校验结果字段是否覆盖计划字段，禁止回答出现数据库没有的产品事实。

通过标准：模型不能扩大查询权限、删除原话中的明确条件、生成 SQL 或绕过产品执行器。

### 阶段 5：建立 LLM Adapter（P1，2～3 天）

新增统一适配层，至少提供：

```text
parse_request()
repair_structured_output()
rank_candidates()        # 过渡能力，最终推荐排序应逐步规则化
format_non_product_answer()
```

适配层统一处理：

- API 地址和模型配置；
- 超时、重试、退避和最大 token；
- JSON 模式和 schema 校验；
- Prompt 版本；
- 模型耗时和错误日志；
- 脱敏后的请求记录；
- 供应商切换。

意图、规划、推荐和话术模块不再直接调用 OpenAI 兼容客户端。

通过标准：替换模型供应商或模型名称不需要修改业务模块；模型调用失败时能稳定进入统一降级策略。

### 阶段 6：补齐产品数据模型（P1，1～2 周）

先保持现有 `product_records` 可用，再逐步补充正式模型，避免一次性迁移造成业务中断。

优先级如下：

1. 产品别名表：简称、旧型号、销售叫法、用户口语；
2. 产品取值目录：颜色、材质、系列和出货地的标准值及别名；
3. 库存表：仓库、可用数量、预留数量、更新时间；
4. 价格表：价格类型、生效时间、失效时间、来源和版本；
5. 租户字段和产品可见范围；
6. 产品发布版本和数据来源追踪；
7. 需要时再把复杂组件和扩展属性从 JSONB 拆成独立表。

数据库变更使用正式迁移工具管理。每次迁移都要提供回滚或可恢复备份，不能继续依赖启动时隐式改表。

通过标准：产品查询可以明确区分公开售价、主体价、成本价、当前库存和历史价格；别名不会依赖模糊搜索猜测。

### 阶段 7：补齐租户、权限和安全边界（P1，1 周）

任务：

1. 从企业微信身份建立不可由用户消息修改的 `tenant_id、user_id、department、roles、scopes`；
2. 把权限判断从单个 `can_view_cost` 扩展成字段能力矩阵；
3. 明确产品范围、成本价、供应商、出货地、库存和内部备注的权限；
4. 查询计划生成前做应用层权限审查；
5. 数据库层补充租户条件，条件成熟后启用 PostgreSQL RLS；
6. 权限拒绝要返回稳定错误码并写审计；
7. 增加越权、跨租户、提示词注入、敏感字段泄露和超大结果集测试。

通过标准：用户消息无法提升权限；任何 SQL 查询都不能脱离租户和发布状态边界；权限拒绝成功率为 100%。

### 阶段 8：固定推荐和回答生成（P1，3～5 天）

推荐流程改为：

```text
模型抽取用户条件
        ↓
数据库筛出候选
        ↓
服务端固定规则排序
        ↓
基于候选事实生成回答
```

排序规则放在版本化配置中，例如：

1. 在售优先；
2. 有库存优先；
3. 满足用户明确条件优先；
4. 销量降序；
5. 更新时间降序；
6. 型号或序号作为稳定的最终 tie-breaker。

缺少销量或库存时必须有确定行为，不能让模型自行猜测权重。

产品回答优先使用确定性渲染器。若需要模型润色，只能把已查询结果、允许展示字段和回答预算传给模型，并对最终答案做字段覆盖和事实来源校验。

通过标准：同一数据、同一计划重复执行得到相同排序；回答不出现查询结果之外的型号、价格、材质或库存。

### 阶段 9：影子运行和分阶段切换（P0，1～2 周）

新链路上线前先不改变用户答案，只做旁路计划生成和对比：

1. 旧 V2 正常回答；
2. 新统一语义入口只读生成 `CanonicalRequest` 和 `QueryPlan`；
3. 比较意图、对象、字段、筛选、权限、分页、回答候选和耗时；
4. 记录新链路会澄清、拒绝、回退或改变结果的原因；
5. 对差异进行人工复核；
6. 先切内部测试用户，再切少量真实用户，最后全量切换；
7. 保留配置开关，出现异常时回退到旧执行器。

建议的上线门槛：

- 结构化意图准确率 ≥ 95%；
- 多条件查询完整率 ≥ 95%；
- 指代对象正确率 ≥ 98%；
- 权限拒绝成功率 100%；
- SQL/任意工具注入成功率 0%；
- 产品事实幻觉率接近 0%；
- 计划回退率低于 1%；
- P95 响应时间在可接受范围内；
- 所有线上错误都能通过 request_id 回放。

## 六、必须优先解决的四个问题

如果暂时不做完整数据库重构，最少先完成以下四项：

1. 把统一 JSON 入口前移，避免模型、规则解析器和旧 V2 各自解释一句话；
2. 把 `ProductFocus` 定为唯一可信指代上下文，所有“它/他/这个/第二个”都走同一解析器；
3. 把字段、筛选、权限和回答校验集中到一个服务端边界；
4. 把 200～500 条真实产品问句建成固定评测集，并持续记录回退和澄清原因。

这四项完成后，当前的产品查询质量和可解释性会先得到明显改善，数据库规范化、租户隔离和部署升级可以随后推进。

## 七、风险和回滚

### 主要风险

- 新协议与旧 V2 字段含义不完全一致；
- 模型输出格式改变导致计划大量澄清；
- 新的指代解析误绑定旧上下文；
- 统一入口增加一次模型调用，导致延迟和成本上升；
- 数据库迁移影响现有发布目录；
- Redis 故障时多进程会话状态不一致；
- 推荐规则变化导致业务人员感知结果顺序变化。

### 回滚策略

- 保留 `UNIFIED_QUERY_PLAN_ENABLED` 和新语义入口开关；
- 新链路先影子运行，不直接改答案；
- 新协议失败时只能回退到经过旧校验的 V2，不得绕过权限和参数化查询；
- 数据库迁移先备份，再执行可验证的向前/向后脚本；
- 每次上线保留按 `request_id` 回放的旧计划和新计划；
- 回滚只切换执行路径，不删除新协议日志和评测结果。

## 八、最终验收结果

改造完成后，应当能够用一个 request_id 查到完整链路：

```text
原始问题
  → 语义解析 JSON
  → 指代解析结果
  → 字段/值/权限审查
  → 最终 QueryPlan
  → 参数和执行器
  → 数据库返回结果
  → 最终回答
  → 会话快照变化
```

对于以下问题，系统必须得到稳定结果：

- “LY0601GT-Cu详细信息” → 返回该型号完整已发布资料；
- “他的材质是什么” → 绑定上一轮可信产品，返回 `ABS外壳铜水路`；
- “它还有库存吗” → 只查询当前可信产品的库存字段；
- “价格 100 到 300、黑色、深圳出货的有哪些” → 保留全部三个条件；
- “不要成本价” → 不请求成本价，也不因为默认详情而展示成本价；
- “一共有多少种颜色” → 做颜色去重统计，不退化成产品数量；
- “把图片和视频都发我” → 拆成两个媒体任务；
- 多候选下的“它” → 澄清，不猜产品；
- 无权限访问成本价 → 拒绝敏感字段，不泄露数值；
- 不存在的型号 → 明确查不到，不用相似型号冒充答案。

## 九、删除 V2 回退通道计划

### 9.1 先定义删除范围

当前 V2 不是单独的一段无用代码，而是产品域目前唯一的生产执行路径。它承载了：

- `ProductQuery` 查询契约；
- `product_store.py` 的固定列映射和参数化 SQL；
- 产品详情、列表、比较、统计和分页；
- `_format_product_v2()` 等基于真实结果的回答渲染；
- ProductFocus 的续问和翻页兼容；
- 图片、视频任务与产品查询之间的兼容调用；
- 成本价、内部备注等敏感字段的输出过滤。

你这里说的删除范围，是删除“QueryPlan 审查失败后回退到旧 V2 计划”的通道，而不是删除当前 V2 承载的产品执行能力。

当前的临时链路是：

```text
CanonicalRequest / QueryPlan 审查通过 → V2 执行器
CanonicalRequest / QueryPlan 审查失败 → 保留原 V2 计划 → V2 执行器
```

迁移完成后应变成：

```text
CanonicalRequest
    → QueryPlan
    → ProductExecutor
    → ProductStore
    → ResponseEnvelope
```

QueryPlan 审查失败时只能澄清、拒绝或返回明确的系统错误，不能再拿旧计划继续执行。固定 SQL、分页、回答渲染和权限能力继续保留在正式执行器中。

### 9.2 删除回退通道前的硬性门槛

在满足下面条件以前，不删除回退通道：

1. 生产环境所有产品任务都由统一语义入口生成 `CanonicalRequest`；
2. `QueryPlan` 是唯一生产计划，审查失败不再需要原始 V2 计划兜底；
3. 产品、媒体、详情、列表、比较、聚合、分页和多轮指代均有新执行路径；
4. 新路径连续运行至少两个完整业务周期，并完成内部用户灰度；
5. 固定评测集、真实审计回放和 PostgreSQL 隔离集成测试全部通过；
6. 无权限成本价、内部备注、跨用户指代、跨查询分页和模型注入测试全部通过；
7. 新旧路径在影子运行中的计划差异已经人工复核，QueryPlan 回退率降到 0；
8. Redis 中的历史 V2 会话数据已经过期、迁移或由兼容读取器安全处理；
9. 所有外部脚本、管理台接口、测试夹具和部署文档不再依赖 V2 名称；
10. 已经准备好按版本回滚的部署包和数据库备份。

建议把“连续两个业务周期”定义为至少两周；如果产品查询量很低，则至少完成 500 条真实问句回放，并覆盖全部关键场景。

### 9.3 分四步删除回退通道

#### 第一步：新旧计划并行，但只让新计划回答

完成统一语义入口后，生产请求走：

```text
CanonicalRequest → QueryPlan → 新 ProductExecutor
```

旧 V2 只作为影子路径执行或回放，不再作为 QueryPlan 审查失败时的在线回退。影子结果用于比较：

- 查询对象；
- 字段和筛选条件；
- 权限结果；
- 返回总数和产品 ID；
- 排序和分页；
- 回答中的事实字段；
- 延迟和错误。

#### 第二步：固定正式执行器边界

将当前 V2 承载的执行能力逐步收敛到正式执行器命名。这里改的是内部边界和命名，不是删除 SQL、分页和渲染实现：

| 当前名称 | 目标名称 |
| --- | --- |
| `query_products_v2()` | `execute_product_query()` |
| `_answer_product_v2()` | `execute_product_task()` |
| `_format_product_v2()` | `render_product_response()` |
| `ProductQueryResult` | `ProductResult` |
| `wecom:product-query-v2-validated` | `wecom:product-focus` 或版本化的新上下文键 |
| `v2` / `v2_detail` / `v2_aggregate` | `list` / `detail` / `aggregate` |

这一步只改协议边界和命名，先不进行大规模 SQL 重写。这样可以把“语义迁移”和“数据库重构”分开，降低风险。

#### 第三步：关闭 V2 回退和旧计划写入

确认统一 QueryPlan 稳定后：

1. 删除 `UNIFIED_QUERY_PLAN_ENABLED=false` 的生产回退用途；
2. 删除 QueryPlan 审查失败后保留原 V2 计划的分支；
3. 计划失败统一进入澄清、拒绝或系统错误，不再执行旧计划；
4. 停止写入仅为旧 V2 回退服务的会话结构；
5. 兼容读取器保留一个 TTL 周期，用于读取尚未过期的旧 Redis 数据；
6. 过期后删除 `focus_from_legacy()` 及确实只服务旧回退的状态字段。

#### 第四步：清理回退代码、测试和文档

只有前三步完成后，才执行回退通道的删除：

- 删除 QueryPlan 失败时保留原 V2 计划的函数、分支和配置开关；
- 删除只覆盖回退分支的测试，或改写为新 `ProductExecutor` 契约测试；
- 删除仅服务旧回退的 Redis key 读写代码；
- 删除脚本和部署文档中的 V2 回退模式说明；
- 更新架构文档，使 QueryPlan 直接指向 `ProductExecutor`；
- 用 `rg` 检查生产代码、脚本和文档中不再出现 `v2`、`V2`、`query_products_v2` 等旧引用；
- 运行完整测试、真实数据库集成测试、影子回放和上线冒烟。

### 9.4 不能随 V2 一起删除的内容

以下能力虽然目前被 V2 使用，但属于长期产品能力，必须保留并迁移：

- 参数化 SQL 编译器；
- 已发布目录读取；
- 产品字段白名单和敏感字段过滤；
- 分页、总数、游标和截断信息；
- ProductFocus 的可信 ID 和多轮续问；
- 结果来源、权限、校验和执行轨迹；
- 确定性回答渲染器；
- 产品、图片和视频的结果包装。

### 9.5 删除前的最终检查表

```text
[ ] 生产代码不再有 V2 回退
[ ] 新语义入口是唯一计划来源
[ ] 新 ProductExecutor 覆盖全部产品形状
[ ] 真实回放无未解释差异
[ ] PostgreSQL 隔离集成测试通过
[ ] Redis 旧状态已迁移或自然过期
[ ] 权限和注入测试通过
[ ] 管理台、脚本和部署配置无 V2 依赖
[ ] 版本化回滚包和数据库备份已确认
[ ] 文档、测试和日志字段完成改名
```

达到这张检查表后，可以彻底删除 V2 回退通道；在此之前，保留一个只读兼容读取器是合理的，保留生产回退路径则不再有必要。
