# 自然语言查询与回答输出治理实施计划

## 现状审计

- `intent.py`、`planner.py` 已有意图与 TaskPlan，但模型输出仍由多个解析入口分别约束。
- `product_query.py` 与 `ontology/schema.py` 已有证据校验、敏感字段权限和字段角色；`product_store.py` 使用固定列映射与参数化 SQL。
- `tools/product.py` 已支持 `count`、字段聚合、稳定排序和页码上下文，但结果协议、输出预算和上下文有效期分散在工具内部。
- `graph/state.py` 能持久化 ProductQuery，但缺少统一的 QueryResult/ResponseEnvelope；多任务合并也没有统一的截断指标。
- 审计已有 request_id、计划、校验和执行摘要入口，需补齐结果 envelope、截断/翻页指标与安全失败原因。

## 分阶段实施

1. **结构治理（已实施）**：增加能力注册表、模型 payload 安全拒绝、QueryResult/ResponseEnvelope、字段排序能力声明；保留模型只能提出结构化计划的边界。
2. **执行治理（已实施）**：把结果元数据接入产品执行 trace；继续使用固定列白名单与参数绑定；比较上限、聚合类型和敏感字段由服务端校验。
3. **上下文与输出治理（已实施）**：产品目录/聚合上下文加入用户绑定的短期有效期；生成签名游标；统一字符预算、长字段截断和“下一页/查看详情”引导。
4. **评测与观测（后续）**：扩展脱敏评测集，覆盖 count/aggregate 边界、注入、权限、空结果、长字段、多任务，并将 envelope 指标纳入审计看板。

## 验收标准

- “有几种产品”只能生成 `operation=count`，不要求颜色/材质；字段去重必须显式使用 `operation=aggregate`。
- 模型输出中出现 SQL、表名、任意函数或工具执行字段时安全失败，不能进入执行层。
- 任何字段、聚合、排序和比较数量都必须通过服务端能力注册表与本体校验。
- 数据库查询只使用固定列映射和参数绑定；只读路径不接受模型 SQL。
- 结果具备 `total_count/items/page/page_size/has_more/cursor/truncated/truncation_reason/requested_fields`。
- 普通列表默认 5 条、聚合默认 10 条、比较最多 3 款、媒体最多 5 条；输出超过预算必须确定性截断并给出后续动作。
- 游标绑定用户与查询指纹，过期或篡改后拒绝；查询条件变化时重新从第一页开始。
- 审计至少包含 request_id、计划、校验/权限决定、执行摘要、结果数量、翻页和截断状态。
