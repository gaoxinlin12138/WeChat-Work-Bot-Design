# 本体层（Ontology）设计：给形状管道装一个知识底座

> 与《新架构设计-按查询形状组织》配套。那份设计说"先把问题归成形状"，
> 这份说清**形状是操作、本体是对象** —— 两者相乘才是"能回答的问题空间"。
>
> ```
> 能回答的问题 = 本体（有哪些对象与关系） × 形状（允许哪些操作） × 执行器（真去查）
> ```

---

## 0. 一句话结论

**可以加，而且值得加。** 但要按"**务实本体**"的规模做：

- ✅ **要**：机器可读的领域模型（实体 / 属性 / 取值 / 关系 / 约束），由代码校验
- ❌ **不要**：OWL / 推理机 / 几百个类的学术本体 —— 61 款产品配不上那种复杂度
- ⚠️ **前提**：本体必须**部分自动生成 + 部分手写 + 自动校验**，否则它一定会和库脱节、腐烂

---

## 1. 本体在这里具体解决什么（都是已经踩过的坑）

### ① 分类维度 vs 标识字段（修掉"61 种系列"）

生产上真实出现过：员工问"有几个系列"，系统答"61 款产品一共有 61 种系列"。
因为 `series` 在库里是**逐款登记的产品名**，不是分类维度。

本体能**从声明上**避免这类错误：

```python
color         = Dimension(cardinality=12,  aggregatable=True)   # 可以统计"多少种"
material      = Dimension(cardinality=10,  aggregatable=True)
spray_modes   = Dimension(cardinality=3,   aggregatable=True)
model         = Identifier(unique=True,    aggregatable=False)  # 标识，统计它没意义
series        = Identifier(unique=True,    aggregatable=False)  # ← 就是它
description   = FreeText(  aggregatable=False)
```

系统于是**知道**"对标识符做去重计数是无意义的" —— 不需要每次都靠事后守卫兜。

### ② 派生维度：把"系列"变成真正能答的概念

本体不只描述现状，还能**定义业务概念**。你们的"系列"在业务上其实是**型号族群**：

```
LY0653GDT / LY0653NBT / LY0653GDT-T   →  族群 0653
LY0685GT-Y / LY0685CPT-F              →  族群 0685
```

本体里声明一条派生规则：

```python
family = DerivedDimension(expr="model 的前 4 位数字", label="系列（型号族群）")
```

于是：
- "有几个系列" → **真的有答案**（按族群数），而不是"这个问题没意义"
- "0653 系列有哪些" → 直接命中一个族群，不用员工逐个打型号

**这比"如实说明无法统计"更有价值** —— 后者只是不撒谎，前者是真的解决了需求。

### ③ 值 → 字段（这轮已实现，但要升格）

现在的取值目录是我手工列的字段清单。升格进本体后：

- **个体层自动从库生成**（新上架产品自动进目录，不用改代码）
- 每个个体**归属于某个属性**（"镜面玻璃·镜面" ∈ `color`），于是值放错字段能被确定性纠正
- 支持别名与写法归一（"灰玻璃枪灰" ≡ "灰玻璃·枪灰"）

### ④ 关系：打开现在答不了的一整类问题

现在产品查询是"单表查询"。本体把关系显式化：

```python
Product  --has_many-->  Component
Component --belongs_to--> Supplier
Component --has-->      unit_price (sensitive)
Product  --has_many-->  Media(image|video)
```

于是这些**不需要新增专用代码**就能生成查询：

| 问题 | 需要的本体知识 |
|---|---|
| "哪个供应商供的配件最多" | Component→Supplier + 聚合 |
| "圣冠的配件都用在哪些产品上" | Component→Supplier→Product |
| "0653 和 0685 的配件有什么不同" | 跨实体 compare |
| "有视频的产品有多少款" | Product→Media + 计数 |

### ⑤ 约束（公理）集中检查

| 约束 | 现在的状态 |
|---|---|
| 成本价/采购价仅授权可见 | ✅ 已实现（散在执行层） |
| 备注里不得暴露内部单价 | ✅ 这轮已实现（脱敏） |
| 标识符不得用于聚合 | ⚠️ 这轮才加守卫 |
| 套装价 ≥ 主体价（数据自洽） | ❌ 没有 |
| 每个产品必须有颜色/材质 | ⚠️ 部分检查 |

本体把约束集中声明，由一致性检查**对着真实的库**跑（`domains/consistency.py` 已是雏形）。

### ⑥ 给模型的提示词从"散文"变成"结构化本体"

现在的字段语义是靠一段说明文字喂给模型。改成本体序列化之后：

- 模型看到的是**明确的**"颜色有这 12 个取值、它是分类维度"
- "系列是逐款标识、不能统计"这类关键区别**直接写在提示里**
- 减少乱猜 → 从源头减少"值放错字段"

## 2. 分层：什么手写、什么自动生成（**这是不腐烂的关键**）

| 层 | 内容 | 来源 | 理由 |
|---|---|---|---|
| **模式层** | 实体、属性、维度/标识、别名、关系 | **手写** | 业务语义必须人判断 |
| **个体层** | 字段取值（12 种颜色、10 种材质…） | **自动从库生成 + 缓存** | 会随上架变化，手维护必然腐烂 |
| **派生层** | 族群等派生维度 | **手写规则 + 自动计算** | 规则是业务的，值是算的 |
| **约束层** | 权限、脱敏、自洽性 | **手写声明 + 自动校验** | 有人写、有代码查 |
| **投影层** | 喂给模型的提示词 | **自动生成** | 保证模型看到的与本体一致 |

**核心原则：凡是会随数据变的东西，一律自动生成；凡是需要业务判断的，手写但由代码校验。**

## 3. 目录结构

```
app/ontology/
  schema.py        ① 实体与属性（手写）：Product/Component/Media/Policy/Script
                   每个属性声明 value_type / cardinality / is_dimension /
                   is_identifier / sensitive / aliases
  values.py        ② 个体层：从 active_product_catalog 生成 + TTL 缓存
                   提供 value → property 的反向索引与写法归一
  dimensions.py    ③ 派生维度：family（型号族群）等规则
  relations.py     ④ 关系（手写）：Product–Component–Supplier–Media
  constraints.py   ⑤ 约束声明 + 对库的一致性校验
  prompt.py        ⑥ 序列化成模型提示词（取代现在的散装语义说明）
```

### 现有代码的去向（不是重写）

| 现在 | 去向 |
|---|---|
| `product_query.py` 里的 `PRODUCT_FIELD_CATALOG` | → `ontology/schema.py` |
| 这轮加的 `product_text_field_values()` | → `ontology/values.py` |
| `product_field_semantics_prompt()` | → `ontology/prompt.py`（由 schema 生成） |
| `domains/consistency.py`（15 条检查） | → `ontology/constraints.py` |
| `_resolve_product_filter_values()` | 改调用 `values.py`（逻辑保留） |

## 4. 与形状管道怎么接

```
                        ┌─────────────────────────┐
                        │      本体层              │
                        │  对象 / 属性 / 取值 /     │
                        │  关系 / 派生 / 约束       │
                        └───────┬─────────────────┘
                                │ 供知识与校验
        ┌───────────────────────┼────────────────────────┐
        ▼                       ▼                        ▼
  ① 形状解析              ② 形状校验                ⑥ 提示词
  知道有哪些对象、         值→字段（查个体层）       把本体喂给模型
  哪些操作合法             维度/标识（查schema）
                          权限/约束（查constraints）
```

**本体不替代形状，而是让形状有依据：**

| | 本体回答 | 形状回答 |
|---|---|---|
| 问题 | **有哪些东西、它们之间什么关系、什么值合法** | **允许对它做什么操作** |
| 例子 | 颜色是维度、系列是标识、配件属于产品 | 计数 / 排序 / 筛选 / 对比 / 明细 |

**两者相乘才构成可枚举的问题空间** —— 这也是"能回答的问题"第一次有了**边界**：
在边界内必须答对，在边界外明确说"这不在我能查的范围内"。

## 5. 落地顺序（低风险 → 高价值）

| 阶段 | 做什么 | 风险 | 收益 |
|---|---|---|---|
| **O1** | 把 `PRODUCT_FIELD_CATALOG` 搬进 `ontology/schema.py`，加上 `is_dimension` / `is_identifier` 声明；聚合守卫改读声明 | 低（搬移+加字段） | 修掉"61 种系列"整类问题 |
| **O2** | 取值目录搬进 `ontology/values.py`，个体层从库自动生成 | 低 | 值→字段、写法归一自动扩展 |
| **O3** | `ontology/prompt.py`：提示词由 schema 生成 | 低 | 模型少猜 → 少一类错误 |
| **O4** | 派生维度 `family`（型号族群） | 中 | "有几个系列"**真的有答案** |
| **O5** | 关系层 + 跨实体形状（供应商聚合、配件对比） | 中 | 打开一整类新问题 |
| **O6** | 约束层集中 + 一致性校验扩充 | 低 | 防止本体与库脱节 |

**建议先做 O1 + O2**（都是搬移 + 加声明，不改行为，风险低），做完你就能看到
"维度/标识"这个区分让多少类问题变成**构造上正确**。

## 6. 必须说清的三条边界

1. **本体不会自动让系统答对所有问题。**
   它改变的是"系统知道什么"。要答对还需要对应的形状与执行器。
   完整公式：`能回答的问题 = 本体 × 形状 × 执行器` —— 缺一环就不行。

2. **本体必须由代码校验，否则它只是一份会腐烂的文档。**
   必须有一条测试：**本体声明 ↔ 真实库** 的一致性（例如 schema 说 color 是维度，
   库里却有 61 个取值 → 直接失败）。这轮"61 种系列"的教训就是这个。

3. **不要过度建模。**
   61 款产品不需要推理机。务实本体的判断标准是：
   **每一条声明都能指向一处代码或一条测试** —— 否则就是装饰。
